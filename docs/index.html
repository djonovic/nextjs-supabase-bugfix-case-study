Fix 01 · auth / session

Logged out after an hour — refreshed cookies never reached the browser

Symptom

Users were signed out about an hour after logging in (the default access-token lifetime), often mid-task. Auth logs showed Invalid Refresh Token: Already Used.

Root cause

  • @supabase/ssr refreshed the token and called setAll(), but the middleware wrote the new cookies to the request only and returned an older response.
  • getSession() on the server trusts the cookie without verifying it, so a forged cookie passed the /dashboard gate.
BEFORE · middleware.tsfull file
const response = NextResponse.next()
const supabase = createServerClient(url, anonKey, {
  cookies: {
    getAll() { return request.cookies.getAll() },
    setAll(cookiesToSet) {
      // refreshed tokens go to the request only
      cookiesToSet.forEach(({ name, value }) =>
        request.cookies.set(name, value))
    },
  },
})
// decodes the cookie, does not verify it
const { data: { session } } = await supabase.auth.getSession()
if (!session && isDashboard) return redirectToLogin()
return response   // has no new cookies
AFTER · middleware.tsfull file
let response = NextResponse.next({ request })
const supabase = createServerClient(url, anonKey, {
  cookies: {
    getAll() { return request.cookies.getAll() },
    setAll(cookiesToSet) {
      cookiesToSet.forEach(({ name, value }) =>
        request.cookies.set(name, value))
      response = NextResponse.next({ request })
      cookiesToSet.forEach(({ name, value, options }) =>
        response.cookies.set(name, value, options))
    },
  },
})
// verified with Supabase Auth
const { data: { user } } = await supabase.auth.getUser()
if (!user && isDashboard) return redirectToLogin()
return response   // carries the refreshed cookies

Fix 02 · row level security

RLS was “enabled” — and still leaked every workspace's tasks

Symptom

Maya, a member of Maple Studio only, could load Cedar Labs' tasks, including “Confidential: pricing change for enterprise plan”. The dashboard showed RLS as enabled.

Root cause

The policy's EXISTS only checks that the user belongs to some workspace. It is never tied to the row's workspace_id, so it is true for every logged-in user and every row.

BEFORE · policyfile
CREATE POLICY "members can read tasks" ON public.tasks
  FOR SELECT TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM public.workspace_members wm
      WHERE wm.user_id = auth.uid()
      -- missing: AND wm.workspace_id = tasks.workspace_id
    )
  );
AFTER · policy + indexfile
CREATE POLICY "members can read tasks" ON public.tasks
  FOR SELECT TO authenticated
  USING (
    workspace_id IN (
      SELECT wm.workspace_id FROM public.workspace_members wm
      WHERE wm.user_id = (SELECT auth.uid())
    )
  );

CREATE INDEX workspace_members_user_id_idx
  ON public.workspace_members (user_id, workspace_id);

Fix 03 · query performance

“My open tasks” read 500k rows to show 50

Symptom

The dashboard list got slower as the table grew. The query: .eq('workspace_id').eq('assignee_id').neq('status','done').order('created_at', desc).limit(50).

Fix

CREATE INDEX tasks_open_by_assignee_idx
  ON public.tasks (workspace_id, assignee_id, created_at DESC)
  WHERE status <> 'done';

Equality columns first, then the sort column, partial on open tasks, so Postgres walks the index in order and stops at 50 rows. Use CREATE INDEX CONCURRENTLY on a live database.
